# Phase 3 — RAG Generation and Citations

## 1. Purpose

Phase 3 turns retrieval results into a grounded answer generated by a local Ollama model. The
generation layer owns prompt selection, context formatting, approximate context budgeting, LLM
calls, token streaming, citation metadata, latency measurement, and persistence of reproducibility
metadata.

The key design rule is that the model receives only retrieved document chunks as evidence and is
explicitly instructed to decline questions that the context cannot answer.

## 2. Exit criterion

Phase 3 is accepted when:

- A question retrieves tenant-scoped chunks.
- Retrieved chunks are formatted with document, page, and chunk identity.
- The configured versioned prompt is loaded from disk.
- Ollama produces an answer using the configured model and generation parameters.
- Answers contain inline `[SOURCE N]` references when supported.
- The structured response includes genuine page-level source metadata.
- Retrieval, generation, and total latency are returned.
- Prompt/model/chunk/parameter metadata is persisted for each non-streaming answer.
- Questions with no retrieval results return the configured insufficient-context response without
  calling the LLM.

## 3. Implemented request pipeline

```text
Question
   │
   ├─ RetrievalService.search
   │    └─ dense/hybrid/reranked SearchResult records
   │
   ├─ load configured prompt version
   ├─ format and budget retrieved context
   ├─ construct system and user prompts
   ├─ call Ollama /api/generate
   ├─ build structured citations from included chunks
   ├─ measure retrieval/generation/end-to-end latency
   └─ persist generation run metadata in SQLite
```

If retrieval returns an empty list, the pipeline skips prompt loading and Ollama entirely and
returns the configured insufficient-context sentence.

## 5. Prerequisites

Phase 2 must already be functional: documents must be ingested and indexed, and retrieval must
return the expected chunks before an LLM is introduced.

Start services and install the configured model:

```bash
make install-ml
make services-up
docker compose exec ollama ollama pull llama3.2:3b
```

For a host-installed Ollama, use:

```bash
ollama pull llama3.2:3b
ollama list
curl http://localhost:11434/api/tags
```

## 6. Generation configuration

```yaml
generation:
  provider: ollama
  base_url: http://localhost:11434
  model: llama3.2:3b
  model_version: llama3.2:3b
  prompt_version: rag-v1
  prompt_dir: prompts/rag
  max_context_tokens: 4096
  max_output_tokens: 512
  temperature: 0.0
  timeout_seconds: 120
  insufficient_context_message: >-
    The available documents do not contain enough information to answer this question.
```

| Field | Meaning |
|---|---|
| `provider` | LLM adapter; currently `ollama`. |
| `base_url` | Ollama HTTP origin without a required trailing slash. |
| `model` | Exact model tag sent to Ollama. |
| `model_version` | Reproducibility label returned and persisted. Keep it aligned with actual weights. |
| `prompt_version` | Requested prompt identifier, such as `rag-v1`. |
| `prompt_dir` | Directory containing versioned YAML prompt files. |
| `max_context_tokens` | Approximate input-context budget assigned to retrieved passages. |
| `max_output_tokens` | Ollama `num_predict` maximum. |
| `temperature` | Ollama sampling temperature; zero is the deterministic default. |
| `timeout_seconds` | HTTP timeout for generation/streaming. |
| `insufficient_context_message` | Exact fallback sentence used by code, prompt, and evaluator. |

Example overrides:

```bash
export RAG__GENERATION__MODEL=llama3.2:8b
export RAG__GENERATION__MODEL_VERSION=llama3.2:8b-q4_K_M
export RAG__GENERATION__PROMPT_VERSION=rag-v2
export RAG__GENERATION__TEMPERATURE=0.1
export RAG__GENERATION__MAX_OUTPUT_TOKENS=768
ragctl config-show
```

`model_version` is a label, not an Ollama inspection mechanism. Operators are responsible for
recording a sufficiently precise value when reproducibility requires a quantization or digest.

## 7. Prompt versioning

Prompt files are YAML mappings with three keys:

```yaml
version: rag-v1
system: >-
  System instructions...
user: |-
  Context:
  {context}

  Question: {question}

  {insufficient_context_message}
```

The user template must preserve these Python format placeholders:

- `{context}`
- `{question}`
- `{insufficient_context_message}`

Prompt lookup first checks `<prompt_dir>/<prompt_version>.yaml`. When the configured identifier
starts with `rag-`, it also checks the suffix filename. Therefore `rag-v1` resolves to `v1.yaml`.
The response and database use the configured identifier (`rag-v1`), while each YAML file also
declares its own version for human review.

The included prompt versions are separate files so experiments produce reviewable diffs instead
of hidden string changes in Python.

## 8. Context formatting

Each included retrieval result is formatted as:

```text
[SOURCE 1]
document_id: doc_...
filename: NIST-SP-800-207.pdf
page: 4
chunk_id: chk_...
text:
<chunk text>
```

Source numbers are assigned in final retrieval order. When reranking is enabled, source 1 is the
highest reranker result, not necessarily the highest raw dense or BM25 result.

The context budget uses a dependency-free estimate of four characters per token:

```text
maximum context characters = max_context_tokens × 4
```

Complete source sections are appended until the next section would exceed the budget. If more
than 200 characters remain, the next section is truncated to consume the remaining budget and is
still included in citation metadata. This estimate is conservative plumbing, not exact model
tokenization. Prompt/system/question tokens are not subtracted from `max_context_tokens`.

For strict context-window enforcement, a future provider-specific tokenizer should replace the
character estimate and reserve explicit space for instructions, question, and output.

## 9. Ollama request contract

Non-streaming requests are sent to:

```text
POST <base_url>/api/generate
```

Payload shape:

```json
{
  "model": "llama3.2:3b",
  "system": "...",
  "prompt": "...",
  "stream": false,
  "options": {
    "temperature": 0.0,
    "num_predict": 512
  }
}
```

HTTP errors are raised to the caller. The generation service does not silently substitute a
different model or fabricate an answer when Ollama is unavailable.

## 10. Structured response contract

`ragctl ask ... --json` returns:

```json
{
  "answer": "Zero trust removes implicit trust based on location. [SOURCE 1]",
  "sources": [
    {
      "document_id": "doc_...",
      "filename": "NIST-SP-800-207.pdf",
      "page": 4,
      "chunk_id": "chk_...",
      "score": 0.89
    }
  ],
  "model": "llama3.2:3b",
  "prompt_version": "rag-v1",
  "latency_ms": 3210.0,
  "retrieval_latency_ms": 85.0,
  "generation_latency_ms": 3125.0,
  "retrieved_chunk_ids": ["chk_..."],
  "generation_parameters": {
    "temperature": 0.0,
    "max_output_tokens": 512,
    "max_context_tokens": 4096
  }
}
```

The `sources` array describes the chunks supplied to the LLM. It is not derived by parsing which
`[SOURCE N]` markers the model actually emitted. Consequently, downstream presentation code can
show available evidence, but citation-marker correctness must still be evaluated separately.

All citations are page-level because ingestion never creates a chunk spanning multiple pages.

## 11. Unsupported-question behavior

There are two rejection paths:

1. If retrieval returns no chunks, Python returns the exact configured insufficient-context
   message, reports zero generation latency, returns no sources, and does not call Ollama.
2. If retrieval returns chunks that do not answer the question, the versioned prompt instructs
   the model to emit that same exact message.

The second path depends on model instruction-following. Because the service currently includes
retrieved sources even if the model itself declines, the strongest automatic rejection guarantee
comes from a well-calibrated dense threshold and a representative adversarial evaluation set.

## 12. Generation metadata persistence

Every call to `GenerationService.answer` inserts a row into SQLite table `generation_runs`:

| Column | Stored value |
|---|---|
| `run_id` | Random `run_<uuid hex>` identifier. |
| `question` | Original user question. |
| `answer` | Final answer or fallback sentence. |
| `prompt_version` | Configured prompt version. |
| `model_version` | Configured model-version label. |
| `retrieved_chunk_ids_json` | Ordered JSON list of included chunk IDs. |
| `generation_parameters_json` | Sorted JSON object of temperature and token budgets. |
| `latency_ms` | End-to-end latency. |
| `created_at` | UTC ISO-8601 timestamp. |

This makes prompt/model/retrieval comparisons inspectable after a run. The current schema does
not persist the fully rendered prompt, token counts, Ollama response metadata, or separate stage
latencies.

## 13. Streaming

`GenerationService.stream_answer(question)` performs retrieval and prompt construction, then
iterates newline-delimited Ollama response objects and yields each non-empty `response` token.

If retrieval is empty, it yields the fallback sentence once and returns.

Important current limitation: the developer HTTP API does not expose a streaming endpoint, and
`stream_answer` does not insert a `generation_runs` record or return structured citation/timing
metadata. Non-streaming `answer` is the auditable production path in this phase.

## 15. Developer HTTP API

Start:

```bash
ragctl serve
```

Call:

```bash
curl -X POST http://127.0.0.1:8000/api/ask \
  -H 'content-type: application/json' \
  -d '{"query":"What is zero trust?"}'
```

The endpoint constructs a `GenerationService` around the app's retrieval service and returns the
structured response. The request model accepts `top_k`, but `/api/ask` currently uses configured
retrieval `top_k`; only `/api/search` passes the request override through. This developer API is
unauthenticated and should remain loopback-only.

## 16. Citation interpretation

A citation is structurally valid when its `document_id`, filename, page, and chunk ID match a
retrieved catalog record. Citation correctness additionally asks whether that source supports the
specific claim beside the model's marker.

The implementation guarantees structural provenance for the `sources` array. It does not yet:

- Parse inline markers and remove unused sources.
- Reject nonexistent marker numbers emitted by the model.
- Map individual answer sentences to supporting chunks.
- Verify semantic entailment between a claim and cited text.
- Generate clickable PDF deep links.

Those quality concerns belong in Phase 4 evaluation and future response validation.

## 17. Failure modes and troubleshooting

### Ollama connection refused or timeout

Check `generation.base_url`, container/host networking, model runtime health, and
`timeout_seconds`. A large CPU-only model can exceed the default timeout on cold start.

### Ollama reports model not found

Pull the exact configured tag. Tags are significant; `llama3.2:3b` and `llama3.2` may resolve
differently.

### Prompt version not found

Confirm `generation.prompt_dir`, the configured version, and the `rag-` suffix mapping. Paths are
resolved relative to the process working directory, so run repository commands from the project
root unless an absolute path is configured.

### Prompt formatting raises a key error

YAML prompt braces are interpreted by Python `str.format`. Preserve required placeholders and
escape literal braces as `{{` and `}}`.

### Model hallucinates despite context instructions

First inspect retrieval. Then lower temperature, improve prompt wording, raise retrieval
threshold, reduce irrelevant candidates, enable reranking, and add adversarial questions. A
prompt cannot compensate for systematically irrelevant context.

### Sources are present for a refusal

That can happen when retrieval returned chunks but the model determined they were insufficient.
The source list represents supplied evidence, not necessarily used citations.

## 18. Security and privacy notes

- Tenant filtering occurs during dense and lexical retrieval; the model receives only those
  resolved chunks.
- Questions, answers, and retrieved chunk IDs are stored in local SQLite. Treat the catalog as
  potentially sensitive conversational data.
- Ollama is configured locally by default. Pointing `base_url` at a remote service changes the
  data boundary and must receive an explicit privacy/security review.
- The developer API has no authentication, authorization, rate limiting, request-size limiting,
  or TLS termination.
- Prompt injection inside documents is not separately detected. The system prompt instructs
  grounding, but retrieved text remains untrusted input.

## 19. Testing

Offline tests inject a fake language model and the in-memory retrieval components. They verify:

- Retrieval results become source metadata.
- Prompt/model/chunk/generation metadata is returned.
- A `generation_runs` row is persisted.
- Page and chunk provenance survive the complete service call.

Run:

```bash
make check
```

Then run a live smoke test against Ollama using known corpus questions. Offline fakes do not
validate Ollama availability, model instruction-following, citation marker behavior, or answer
quality.
